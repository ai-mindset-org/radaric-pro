# Radaric — Feature Reference

> The reference for feature behavior. Related: [API_REFERENCE.md](API_REFERENCE.md), [ARCHITECTURE.md](ARCHITECTURE.md).

## Key Features

**Content Collection:** RSS feeds (including bulk import from Feedly/Inoreader via OPML — `POST /api/feeds/import-opml`), **YouTube channels with transcript-based eval** — first-class `SourceType.YOUTUBE`, available on both tiers (no entitlement gate). `Feed.url` stores the canonical `https://www.youtube.com/channel/UC<id>` (Twitter pattern: id extractable purely, no extra column); any paste format (@handle, bare handle, channel/legacy/video URL, feed-XML) resolves once at creation via `resolveYouTubeChannel` (`lib/youtube.ts` — channel-page `og:url`/`canonical`/`itemprop=identifier`; video URLs via oEmbed `author_url`; the page's JSON `"channelId"` markers are deliberately unused — they match related channels). `lib/parsers/youtube.ts` derives the feed-XML URL purely, reads the channel Atom feed (15 latest), and fetches transcripts **only for new videos** (`externalId` = `youtube:<videoId>`; parse-stream pre-queries known ids) — capped at 12k chars, per-item timeout+catch so one dead transcript degrades only its own video to title+description (a first-parse transcript failure is permanent for that video — dedup never re-enriches; accepted tradeoff). Eval uses the global 3k slice; content is ordered header→description→transcript so the relevance signal is front-loaded, and the full 12k stays in the material for reading/story-gen. **Cross-form duplicate guard:** a channel already added as a plain RSS feed-XML URL answers 409 `DUPLICATE_FEED` by channel-id containment (feeds POST + save-feeds); OPML import upgrades `videos.xml?channel_id=` entries to native YOUTUBE. Cover = channel avatar via og:image; favicon skipped on purpose (generic youtube.com icon). Brand `#FF0000` appears only as the type-card icon glyph (dark `#e5484d`); red **text** uses the AA token idiom (`bg-red-500/15 text-red-700 dark:…red-400`). **Branded RSS presets** — Substack, Bluesky, Mastodon, Product Hunt, GitHub, arXiv surface as first-class source cards ("Popular sources" on `/feeds`) but stay plain `type: RSS` underneath: the brand "flavor" is derived on read from `Feed.url` via the pure registry `lib/feed-flavor.ts` (no DB column; icons/colors live in the client leaf `components/feeds/flavor-icons.tsx`), brand handle/slug/URL inputs resolve to feed URLs in the feed form (with an editable resolved-URL escape hatch) and in bulk-add/onboarding extraction (`resolveStatus()`), duplicate adds answer 409 `DUPLICATE_FEED`, and titleless feeds (Bluesky) get a lede title via `pickItemTitle()` — the first sentence of the snippet (`derivePostTitle()`, `lib/title.ts`) rather than a capped copy of the whole thing. Telegram channels (including private via GramJS) — posts render their Telegram message formatting (bold, italic, underline, strike, spoiler, inline code, code block, blockquote incl. collapsed, links, mentions, email/phone); card and story excerpts stay inline-only, while block elements and the interactive spoiler/collapsed-quote leaves render on the detail surfaces (`lib/telegram-entities-to-react.tsx`, `lib/telegram-rich-text-leaves.tsx`); **Telegram media (RAD-359):** every post format is mirrored to R2 and rendered — photos, videos (incl. round video notes), GIFs/animations, voice messages, audio, stickers, documents/files (≤50MB; a larger video keeps its poster plus a `tg://too-large/<channel>/<id>` marker that `components/materials/material-media.tsx` draws as "Media not mirrored · Open in Telegram"), polls (question + options in `content`) and mixed albums (all members, ascending; an album cut by the fetch window is completed by one fetch of its own missing members, and one whose member the channel deleted keeps the rest). One parse path (`lib/story-aggregator/telegram-media.ts` + `worker-helpers`) mirrors the whole parse in one batch through the worker, with a 75s media budget and concurrency 3, so a media-heavy parse stays inside the parser's 120s timeout; media already in R2 is never downloaded again (a HEAD on the deterministic `telegram/<channel>/<id>.<ext>` key, fail-open), so a re-parse spends the budget only on posts still missing theirs; a document's largest Telegram thumb is uploaded as the poster (`telegram/<channel>/<id>_thumb.jpg`, `uploadTelegramThumb`) so video cards get a cover and a play badge. Media kind is inferred from the URL (`mediaKindFromUrl`, no schema change); the reading surfaces render each kind via `MaterialMedia` (video/audio players, document rows; a post whose only media is one video plays it in the hero, on its poster), and `detailGalleryMedia` keeps playable/file entries while still dropping unknown pages (Parallel `source_urls`). A re-parse reconciles rows stored before the feature (`lib/story-aggregator/media-backfill.ts`, media/content only — never AI, status or feedback), and an operator script (dry-run default, run in-container) re-mirrors older posts by message id through the worker. — Twitter/X (TwitterAPI.io — tweet text run through the same `derivePostTitle()`, falling back to the linked page's `og:title` then a `Kind from @user` label when the tweet itself yields no headline; `content` keeps the verbatim tweet, and the card excerpt and the reading page both render the derived headline and only what follows it, so card and post page show the same title). A derived headline keeps the lede's own link and nothing else — a link inside the first sentence stays clickable on both surfaces (`components/materials/material-title.tsx`; Telegram entities are re-mapped onto the stored title by `lib/title.ts` `remapToDerivedTitle`, HTML is cut out of the stored markup and sanitized to its anchors by `derivedTitleHtml`), while bold, italic, underline, strike, code and spoiler formatting is dropped so the title reads as one plain run of type (RAD-365) — falling back to the plain stored title when a cut that doesn't read back as the title's own words would change what the headline says. AI-powered web monitoring (Parallel Monitor API), media content, smart deduplication. **Article-page images (RAD-336 / RAD-340):** the `<img>` tags of the page an item links to (absolute after base-URL resolution, at least 200px when they declare a size, capped at 24 in document order) are appended to `mediaUrls` after all feed-level media and the og:image — taken from Readability's article, and, when the article kept none (Readability picks its container by text, so a text-less portfolio grid is dropped whole), from a fallback scan of the page DOM that admits only images declaring a real size; the cover stays feed-level — an article image may become one only when the feed offers no media and it passes `isRenderableImageUrl` — Behance `project_modules/<size>/<file>` variants fold in `sameImageKey` so one file is one card frame (the feed's 404px crop is left alone), and a card's cover gallery caps at 16 frames. **One per-source override (RAD-432):** on Land Book the feed body's `/image/0x0:…-screenshot` crop — extensionless, so `isRenderableImageUrl` admits it by predicate — leads both the card gallery and the detail hero, while Landbook's own `-og-image`/`og-media` card and the article page's other widths of the same shot are dropped from both; rows already stored are corrected by the same URL rules with no backfill, and every other feed keeps the og:image-first cover. A page behind a `403` cookie challenge (Behance's CDN: `document.cookie = "js_challenge_value=<hex>"` + reload) is answered once — the value is read from the body, the same URL is re-requested with that cookie, and the cookie is remembered per host so only the fetches already in flight before the host's cookie is known pay the extra round trip (5 of 20 on the live feed, one per concurrency slot); a 403 without the challenge, or a second 403, still falls back to the feed text (RAD-391, `fetchArticlePage` in `lib/parsers/rss.ts`). The page fetch goes through `safeFetch`, so every redirect hop is checked against `isAllowedUrl` before it is requested, and `Cookie`/`Authorization` headers are dropped once a hop leaves the original origin (RAD-392). A 2xx bot-check interstitial ("A required part of this site couldn’t load…", Sucuri's JS redirect) is a failed fetch, logged with its host and never stored as content; a Behance gallery that is still blocked — that interstitial, or a 403 the cookie answer did not clear — is read once through `r.jina.ai`, a headless-browser reader, and its gallery is that project's own `project_modules` files (anchored on the project id, one per file, `max_3840_webp` stills stored at `1400_webp`, ≤ 24); at most two reader requests run at once per process (keyless limit 20/min; `JINA_API_KEY` raises it), and any reader failure leaves the item on its feed media. Article pages are fetched **only for items not yet stored** — `parseRSSFeed(url, { knownItems })`, fed by `knownMaterialKeys(sourceId)` (`lib/materials/known-keys.ts`) from both parse routes; a failed lookup fails open (RAD-395). Bulk parsing uses a single SSE connection (`GET /api/parse-stream`) — server processes feeds concurrently via `p-limit`, replacing the previous client-side batching approach. The run is **server-owned (RAD-346)**: a dropped transport no longer skips sources or logs fake source errors — a CDN or reverse proxy in front of the app can truncate that stream, so the route finishes every source, the card goes **detached** and polls `GET /api/parse-stream/status` (4 s, bounded) until it can settle with the server's reconciled results, and only `POST /api/parse-stream/stop` (wired to the card's Stop) ends a run early — one run per user at a time. Any tab can watch it (**RAD-347**): the posts page checks that endpoint once on mount and adopts a run it did not start (attach beats the automatic onboarding parse; a `/feeds/[id]` card never adopts the account-wide run), the server's "already running" refusal detaches the card instead of failing it, and one unusable status answer is tolerated before a detached run is reported as dropped. The stream is hang-proof by design: every AI eval call carries an `AbortSignal.timeout` (`AI_EVAL_TIMEOUT_MS`) + explicit `maxRetries`, and each source is wrapped in a per-source watchdog (`SOURCE_TIMEOUT_MS`, `Promise.race`) so no single hung source or AI request can stall `parse_complete`. Note: `maxDuration` in the route is a Vercel-only directive and is ignored on Railway, so these in-code timeouts are the only time fuse.

**AI Filtering:** Global + per-feed prompts — **per-feed criteria take precedence over the global prompt**: a source-specific exclusion is a hard veto (a material is FILTERED even if it passes the global criteria), enforced by a conditional `# PRECEDENCE` preamble + a shared `EVALUATION_PRIORITY_RULES` constant in `lib/ai.ts` (veto scoped to the source's custom prompt; disliked categories and feedback stay soft preferences). Confidence scoring is display-only — the approve/filter decision is the AI's `relevant` boolean, with no confidence-threshold gate. Feedback knowledge base (per-material Like/Dislike with material context in prompt, per-feed categories; up to 30 most recent per-source and 150 global feedbacks used per evaluation; explicit commented feedback propagates cross-source — a comment written on one source is included in the AI context for all other sources; bare Like/Dislike stays source-scoped), implicit feedback on user overrides, blacklists, batch processing. Accuracy tracking via `GET /api/analytics/accuracy?days=30`. **Run AI Rules:** Re-evaluates all non-archived materials against current rules via `GET /api/posts/refilter` (SSE, abort-on-disconnect); "AI Rules" button in posts toolbar with live progress counter. **Story Aggregation:** Approved materials are grouped into stories **only when ≥2 posts genuinely match** (post↔post or post↔existing-story) — a lone approved post is **never** auto-wrapped into a single-material story, so individual source posts always render verbatim (a single-material story's AI summary would otherwise replace the original via `buildRenderItems`). The unified matcher (`matchContent`, `story-matcher.ts`) scores existing stories **and** standalone candidate posts in one pass via 4-signal pre-filter scoring (title, content, cross-language entity overlap, domain) + event-identity AI matching (groups only the SAME specific underlying event, not same topic/company; when-in-doubt-different; full cross-language support), returning `matchType: "story" | "material" | null`; a `requireSignal` guard skips the AI call when no candidate shares signal. Forming a two-post story is **atomic** — `$transaction` + conditional `updateMany({ storyId: null })`, so a partner grabbed by a concurrent run rolls the whole pairing back (no half-committed/orphan single-material story). The **only** path that creates a single-material story is the explicit manual "send to stories" action (`allowSingletonStory`). Grouping never runs at parse time; it's triggered by the **Group Stories** button (`/api/posts/group-stories`; the pairing candidate pool is global cross-source even when the trigger is feed-scoped, bounded by lookback + cap). One-time backfill `POST /api/admin/dissolve-single-material-stories` (`?scope=self|all`, ADMIN) detaches + deletes pre-existing auto single-material stories (spares Notion-exported, manually-sent, inbox-backed, and multi-source stories). Configurable per-user story model — supports Anthropic and OpenRouter models via `isOpenRouterModel()` auto-routing in both `pipeline-deps.ts` and `worker.ts`. **Story card actions:** Stories use the same `MaterialCard` component as posts (identical layout: AI status, confidence, title, excerpt, badges, actions). Like/Dislike, Archive/Restore, Delete on story cards propagate to all constituent materials via batch `Promise.allSettled` calls with partial failure rollback. Delete forwards user feedback to the AI knowledge base. Double-width (`sm:col-span-2`) is kept for stories with 4+ source materials; 2-3 source stories use standard card width. `material-card.tsx` handles both posts and stories.

**Interface:** Mobile-first responsive, Linear-inspired OKLCH design system. Material views (Inbox/Approved/Filtered/Archive), feed management with per-type quick-add cards + **bulk "Add feeds" dialog**: toolbar button opens a 3-stage Dialog (paste/upload → SSE discovery via `/api/onboarding/parse-feeds` → inline review grouped by type → save via `/api/onboarding/save-feeds`) — reuses the onboarding pipeline without new endpoints; `FeedTypeCards` still deep-link to `/feeds/new?type=...` for single-feed quick-add. Full-page detail view, light/dark mode. **Feedly-style left sidebar:** persistent collapsible aside under the top bar with an "All" row linked to `/posts`, a **Folders** section and an **Uncategorized** bucket. Sources can be organized into user-created folders (RAD-393): create/rename inline from the section header or a row's kebab (delete confirms in a dialog and keeps the sources), drag a source onto a folder or back to Uncategorized (450ms long-press on touch), or use the equivalent kebab menu (`Move to folder…`, `Remove from folder`, `New folder…` — which files that source in one flow). The menu is the canonical keyboard/touch path; the drag is an enhancement. A folder opens `/folders/[id]` — the same `MaterialsList` grid as `/posts`, scoped to the folder's visible, active member sources: search, filter counts, the source-type filter, Group Stories, AI Rules and Run Parsing all follow the scope, the heading shows the folder name with an "N sources" subtitle, and the account-wide bulk delete is hidden there as on a source page. The folder badge sums its members' inbox counts; collapse state persists in the `folders-collapsed` cookie, and a folder holding the active source renders expanded without overwriting an explicit collapse. Each row icon prefers the site **favicon** (`faviconUrl`, auto-fetched via `lib/feed-favicon.ts` — `<link rel=icon>`/`apple-touch-icon` → verified `/favicon.ico`; null for Telegram/Twitter/Parallel), then the cover/avatar (`coverUrl`), then a type-coloured monogram fallback — RSS orange, Telegram blue, X zinc, Event Trigger purple, shared via `lib/feed-type-color.ts`). Selected row uses the sidebar accent fill (`bg-sidebar-accent`, no leading-edge bar). Uniform `font-medium` across active/inactive rows — no weight jiggle on selection. Click-through opens the per-source view `/feeds/[id]` — the same `MaterialsList` grid and toolbar as `/posts`, with the feed name as the page's sole `<h1>` and a 48×48 cover thumbnail sitting beside it via a shared `leading` slot prop (keyed at creation: it crosses the RSC boundary into a client component). Subtitle shows a brand-tinted type Badge matching the sidebar monogram palette, the URL (trimmed with an ellipsis past 30 chars, or `@handle` for Twitter/X feeds), and the item count. Edit button joins the toolbar via a shared `headerExtra` slot — 44×44 icon-only on mobile (written as `min-h-[44px] min-w-[44px]`, because `--spacing: 0.2rem` makes `h-11` render 35.2px). Group Stories, AI Rules, and Run Parsing are **scoped to the current feed** when invoked here (the three SSE endpoints read `?feedId=` from query params). The source-type control is hidden on per-source views (`hideSourceTypeFilter` prop) **and** `sourceTypeFilters` state is forced to `["ALL"]` with skipped persistence so a cross-page filter from `/posts` can't silently empty the list. Mobile drops the aside for a shadcn `<Sheet>` drawer triggered by the same chevron toggle, dismissed by a visible labelled Close button at the bottom of the drawer (not an X). The chevron uses `window.matchMedia` only inside the click handler — derived state is `isSidebarOpen || isMobileDrawerOpen`, pure React state to avoid SSR/hydrate `aria-expanded` flip. State persisted via an `httpOnly` `sidebar-open` cookie written by `POST /api/ui-state` with a fire-and-forget keepalive fetch (so is `folders-collapsed`) — not a server action, whose cookie write refreshed the route and re-rendered the posts grid mid-toggle (RAD-408); every feed CRUD handler (create, patch, delete, OPML import, onboarding save, fetch-cover, clear-error) calls `revalidatePath("/", "layout")` so the sidebar never goes stale after add/remove/edit. Source link on material cards navigates to `/feeds/[id]` instead of `/feeds/[id]/edit`; `feed-card.tsx` in the management UI still points at `/edit`. Top bar keeps Posts / Feeds / Rules / Library — "All" in the sidebar is an intentional duplicate. Navigation: Posts → Feeds → Rules → Library → Settings. **Onboarding flow** (`/onboarding/feeds` → `/onboarding/unresolved` → `/onboarding/review` → `/onboarding/preferences`): OAuth new users redirect to `/onboarding/feeds` — redirect is handled by the `/posts` server component (checking `onboardingCompleted`) rather than the `signIn` callback, so the JWT cookie is always set first; **revisit rule (RAD-168)** — a user who finished onboarding but has zero non-hidden feeds is sent to `/onboarding/feeds?revisit=1` on a new visit, i.e. the first full page load of `/posts` or `/feeds` after an hour with no Radaric activity (the proxy creates the `radaric_visit` marker only on a non-/api document navigation, lets background requests only extend it, and forwards the verdict as the `x-radaric-new-visit` request header); `?revisit=1` only picks the "Welcome back" copy and hides the Preferences phase, while skip/save destinations come from `onboardingCompleted` (returning → `/posts`, first-time or unknown → preferences, which a server guard closes to completed users); `onboardingCompleted` is never written back to false; feeds persisted via shared `persistFeeds()` helper (retry + toast on failure); content skeleton shown during review load; preference skip has error handling; SSE fetch uses `AbortController` (aborted on Skip/unmount); file upload enforces 5MB server-side limit. Primary action buttons (Find feeds, Save & continue, Start Radaric) are on the right; Skip buttons are on the left across all 3 steps. Stories are always interleaved with posts by date in the unified feed — no separate toggle. Story cards use the same layout as post cards (no separate stacked/wide pseudo-layer variants); double-width (`sm:col-span-2`) applies only for 4+ source stories. Dedicated `/rules` page (Global Prompt, Blocklist, AI Knowledge Base). Feed cover images: auto-fetched on creation (OG/twitter:image for RSS/Twitter, channel avatar for Telegram), manual refresh via `POST /api/feeds/[id]/fetch-cover`. Favicons auto-fetched on creation too (for the sidebar row icon); admin backfill for existing sources via `POST /api/admin/fetch-all-favicons` (`?mode=missing` default, `?mode=all`). **Source type filters** (RSS, Telegram, X, Event Triggers) are multi-select — toggle each independently; "All" resets to unfiltered. Since RAD-318 they live in a checkbox menu behind one trigger rather than a permanent chip row, and the trigger's label is the selection ("All types" / the single type's name / "N types"). See [STYLING_GUIDE.md](STYLING_GUIDE.md). **Detail page enhancements:** Material detail shows an edge-to-edge hero cover (the post's painted cover via `previewImageUrl`, up to 60svh / 80svh on a tall viewport, 40svh in the peek, eager-loaded) filtered from the media gallery below; both material and story detail pages consolidate feedback + action buttons into a single `flex-wrap` row. **Action-bar hierarchy (shared with `material-card.tsx`):** Like / Not relevant stay labeled and focal, pulled left with a first-glyph alignment nudge (`-ml-4` detail, `-ml-2` card); Open / To Notion / Archive-Restore demote to icon-only 16px buttons in an `ml-auto` cluster; Delete separates with its own `ml-2` gap. Hovers are intent-colored — Like green (`hover:bg-primary-subtle`), Not relevant + Delete red (`hover:bg-destructive-subtle hover:text-destructive`), not flat gray. The Save/Bookmark button is not rendered here (see Knowledge Base above). The detail top bar + `<article>` read column is `max-w-[850px]`. "To Notion" button on material detail (gated on `hasNotionIntegration`); story detail shows the primary material's feed name linked to `/feeds/[id]` beside the timestamp.

**Posts surface (RAD-318):** The `/posts` and `/feeds/[id]` screens share one toolbar and one processing surface. **Controls:** a single CSS grid — one row on desktop, two fixed rows on mobile — holding exactly one DOM instance of every control at every width (mobile and desktop differ by grid *placement*, never by `hidden`/`sm:hidden` twins, so there are no duplicate ids and the rows are deterministic rather than wrap-dependent). Scope sits left, action right, at both sizes. The view is a **radio menu** (Inbox / Filtered / In Stories / Archive / All posts) whose trigger is the page heading, so no view other than the current one is on screen while the menu is closed; source types are a **checkbox menu** labelled by its own selection. The heading carries **one number**, always meaning "what is in the grid right now": the view's exact total, replaced by the response's own `total` as soon as a search or type refinement applies, and rendered as *pending* rather than stale while a request is in flight. Group Stories, Run AI Rules and the account-wide bulk delete moved into a More-actions menu; the bulk-delete item names its scope and count explicitly (`Delete all filtered posts (15)`) because the endpoint ignores search, types and source. Mobile targets are written as `min-h-[44px] min-w-[44px]` — `--spacing` is `0.2rem` here, so `h-11` renders 35.2px and no Tailwind height utility below `h-14` reaches the touch floor. On a source page the source name is the sole `<h1>`, the view selector becomes a compact outline trigger beside it, and the type control is hidden. **Processing:** every run — parse, story grouping, AI-rules refilter, and the automatic first parse — is owned by one controller (`use-post-processing.ts`) and shown as the **first card in the posts grid** rather than a banner that pushed the grid down as it grew. The card's height is a fixed `min-h-[300px]` budget in every state at every breakpoint, so a streamed event can never change it — `AnimatedGrid` measures every live cell on every commit and would otherwise re-animate the whole viewport on each frame of a parse. Its log scrolls inside its own budget, is `aria-live="off"` and a plain list (never `role="log"`, which would announce every line); the one announced region is a polite, atomic summary that updates on phase change and on each source settling. Stop while running, Dismiss once terminal — never both — and dismissal returns focus to the Run-parsing button. A **run-generation guard** is what makes Stop real: a stopped or superseded run's frames are dropped by the reducer, so there is no automatic next phase and no late success. **First run:** server-owned and merely observed (see [ONBOARDING.md](ONBOARDING.md)). **Last checked (RAD-424) — hidden since 2026-11-05:** `FRESHNESS_LINE_VISIBLE = false` in `lib/materials/source-freshness.ts` keeps the line off every posts surface until a new place is chosen; the queries, summary and last-run recorder below stay wired. nothing polls in the background, so the heading block carries a muted line directly under the scope's name (the source or folder name, or the view word on `/posts`) — `Checked 12 min ago` — built from `Feed.lastParsedAt` (`lib/materials/source-freshness.ts`): the OLDEST check among the scope's active sources (`/posts` = every non-hidden feed, `/feeds/[id]` = that feed, `/folders/[id]` = its members), plus `· N not checked yet` / `· N failed`; paused sources are not mentioned, a lone errored feed reads `Last check failed`, a lone paused one `Paused · checked …`. The tooltip and an sr-only sentence always say sources are checked when you run parsing (`MANUAL_CHECK_NOTE` — never imply polling). After a parse settles with success or partial, its "New posts" number (`collectedCount`, the processing card's own) is kept per scope in `localStorage` (`radaric:last-run:*`) and becomes the headline (`5 new posts · checked 3 min ago`, `No new posts · …`) until the server value is more than 10 minutes newer (another device parsed). The `/feeds` card badge uses the same relative formatter.

**Side peek — posts and stories open beside the list (RAD-345):** a toggle beside the view menu on `/posts` and `/feeds/[id]` switches a card click between the full-page route (default) and a peek: a **full-height** panel docked right from `lg` up (no corner rounding, no shadow — `bg-card` plus one hairline), and an iOS-like bottom sheet below it (grab handle, backdrop, swipe-down dismissal; the drag only starts from the handle, only at the top of the content, and `prefers-reduced-motion` collapses the settle while keeping the gesture). The panel reproduces the page's composition rather than shrinking it: the article is the same reading column (`max-w-[850px]`, the page's gutter) centred inside a panel ~two thirds of the viewport, and it repeats no title of its own. A click outside closes it (except on the excerpt pill, which is portaled to `<body>` but belongs to the article). The preference is per device (`localStorage['radaric-open-mode']`, default `page`) and applied after hydration. The open target lives in the URL (`?post=` / `?story=`, native History API — no server round-trip, so opening, swapping and closing issue no RSC request): opening pushes one entry, later targets replace it, closing rewrites that entry back to the list URL, so Back closes the peek and a deep link (`/posts?post=<id>`) opens the panel on first paint. Content reuses the reading surfaces — `MaterialArticle` / `StoryArticle` are extracted from `/posts/[id]` and `/stories/[id]`, and the peek reproduces the page's own reading column (`PeekColumn`: `max-w-[850px]`, `px-5 sm:px-4`, the card's `sm:p-8` inset — everything but the card's surface), so the same body renders at the same measure in both, including the hero's full-bleed and `MaterialTitle`'s link on a derived headline; only the hero's cap and fetch priority differ, and the media rows size off the article's own width via `@container`. Actions reuse the list's optimistic handlers, so the grid updates behind the panel. The peek resolves from a copy taken at open, so a `router.refresh()` or a parse finishing cannot blank it; archiving the post the panel shows moves it on to the next visible cell — planned before the optimistic update, opened once the request lands, so a failed archive leaves the panel where it failed — and only the last cell of a view (or a target outside it, a deep link into another filter) keeps the panel on the archived copy with Restore; deleting closes it. A story reads `GET /api/stories/[id]` (now returning its constituent materials, the same select the story page uses) with a session cache invalidated after every action; a post renders from the row the list already holds and only fetches on a deep link. The header carries prev/next (the visible grid order, `j`/`k`, disabled at the ends) and Open-full-page; focus moves into the panel and returns to the originating card on close. Cards gained keyboard activation (Enter/Space on the already-focusable card) and a real new-tab path for modified/middle clicks in both modes.

**Appearance → Typography (RAD-363, RAD-386):** every user picks a font for each of four roles — **Headings**, **Text**, **Counters**, **Tags** — from eleven (Inter, Martian Grotesk, PT Root UI, Golos Text, IBM Plex Sans, SF Pro, SF Pro Rounded, Martian Mono, JetBrains Mono, IBM Plex Mono, SF Mono; `lib/typography/fonts.ts`), any font in any role; the section (`components/settings/typography-section.tsx`) sits after Account for users and admins alike, with a live specimen. Presets (`lib/typography/presets.ts`) Inter (= reset), Martian, Apple, PT Root and Plex are one-click chips; when the four selects match none the row reads "Custom". JetBrains Mono's code ligatures (`->`, `!=`, `===`, `<=`, `//`) are disabled in every role through the `-tag` feature syntax (`DESIGN.features` → `"calt" 0`); IBM Plex Mono is a four-file static face (400/500/600/700) — the engine snaps a computed weight to the nearest shipped file instead of interpolating. **Every change applies instantly and saves immediately** — no Save button: the change is optimistic and saves are **serialized** (one `PATCH /api/user-settings` in flight, the newest change queued behind it, `keepalive`, never aborted — an abort would not stop the server's upsert and an older value could land after a newer one); if the latest save fails the UI reverts to the last confirmed choice and toasts "Failed to save font choice". **Storage contract:** `UserSettings.typography` (`Json?`, additive `user_settings` migration) is either the full object `{heading, text, counter, tag}` of registry ids or DB null (= default); the PATCH accepts exactly that — the full four-key object or `null` — and answers 400 before any write on anything else (`validateTypographyInput`); the Inter preset is written as `null`, `PUT` never writes the field. Reading is lenient and never fails (`lib/typography/load.ts`: no row, a poisoned value or a DB error resolve to the default), so rendering never depends on the column. **Scope:** only the `(dashboard)` route group — `app/(dashboard)/layout.tsx` loads the prefs server-side and wraps the shell in `TypographyProvider`, which renders one unlayered `<style data-radaric-typography>` of `--type-<role>-*` remaps (empty for the default); landing, auth and onboarding always render house Inter. **Device notes:** the SF fonts are Apple system fonts and are never shipped; on a non-Apple device the picker shows an inline note naming what is drawn instead (Inter for SF Pro / SF Pro Rounded, the device's own monospace for SF Mono), and SF Pro Rounded needs WebKit (Safari on macOS, any browser on iOS/iPadOS) — elsewhere on Apple it falls to SF Pro and says so; a monospaced Text choice warns that reading is slower. Every combination stays harmonious through the adaptation engine (x-height, cap-height and line-box normalisation, stem-matched weights, a narrow cut for tags, borrowed tabular digits) — see [DESIGN.md → Typography](DESIGN.md#typography) and [STYLING_GUIDE.md → Typography](STYLING_GUIDE.md#typography). The self-hosted Inter 4 also restyles the default for everyone: `cv11` + `ss01` and the `opsz` Display cut, which the Google-served Inter never rendered.

**Multi-User:** Role-based access (ADMIN/USER), full data isolation, admin-only vs personal settings. Telegram feeds and auth available to all users. Story Aggregator settings (`storyInboxChannelId`, `storyNotionDatabaseId`, `autoDeleteTelegramMessages`) are ADMIN-only — enforced at both UI (hidden for non-admin) and API (`PUT /api/user-settings` returns 403 only when a non-admin **sets** one to a real value; a `null`/`false` no-op — which the settings form always sends — is accepted and the field is stripped, so non-admins can still save their personal settings). Worker selects the admin user's channel config (`findFirst` with `user.role = "ADMIN"` filter). Per-user story language setting (`storyLanguage`, default "en") — stories generate in the user's language; Russian rubric list shown only for `ru` users.

**Billing:** Hard paywall after onboarding. Two Stripe tiers — **Pro** ($59/month or $499/year, full feature set) and **Lite** ($9/month or $90/year), identical **except Lite cannot parse Twitter/X account feeds**. The tier is derived live from the subscription's stored `stripePriceId` (no DB column, no migration) via `lib/entitlements.ts` (`planFromPriceId`, `subscriptionIncludesTwitter`, `getTwitterEntitlement`); an unmappable/legacy price id **fails open to Pro** (grandfather). `STRIPE_PRICES` keys are `pro_monthly`/`pro_yearly`/`lite_monthly`/`lite_yearly` (Pro reuses the original `STRIPE_PRICE_MONTHLY`/`STRIPE_PRICE_YEARLY` env vars; Lite adds `STRIPE_PRICE_LITE_MONTHLY`/`STRIPE_PRICE_LITE_YEARLY`). **Twitter is gated, never stored on `Feed`:** blocked at creation (`POST /api/feeds` → 402 `TWITTER_NOT_IN_PLAN`; `POST /api/onboarding/save-feeds` drops X feeds for non-Pro, reporting `twitterSkipped`) and excluded at parse time (`/api/parse` + `/api/parse-stream` add `type: { not: "TWITTER" }`), so a Lite user's retained X feeds are kept + locked in the UI but never fetched, and an upgrade re-enables them instantly. Checkout body is `{ tier, interval }` (transitional union still accepts the legacy `{ price }` = Pro). 30-day money-back guarantee via the configured contact address (`CONTACT_EMAIL`, no self-service refund button). ADMIN role bypasses all gates. Flow: signup → onboarding (full access — onboarding is the product demo) → `onboardingCompleted=true` → `/posts` triggers paywall redirect → `/settings/billing` → Stripe Checkout → webhook updates DB → `/posts`. **Self-hosted mode (RAD-284):** `SELF_HOSTED=true` short-circuits BOTH gates — `hasActiveAccess` and the independent `subscriptionIncludesTwitter` — so self-hosters get every feature without Stripe; `/settings/billing` renders a "self-hosted — all features unlocked" panel, and the Stripe routes keep failing cleanly through the lazy `getStripe()`. The public pages follow the flag too: `/` redirects to `/login`, and `/terms` and `/privacy` render short neutral pages that put the terms and privacy practices on the operator. Usage caps are spend guards and stay in force. **Referral trial (RAD-419):** a NEW account created after a `?ref=<TRIAL_REF>` visit gets `complimentaryAccessUntil = now + TRIAL_DAYS` (7) in the same `user.create` as the account (credential and Google/Apple paths) — Lite, no X, no card; existing accounts get nothing. `proxy.ts` carries the ref to account creation in an httpOnly `radaric_ref` cookie set on `/` and `/signup` (`lib/trial-ref.ts`), and both pages show "7 days free, no card required" for the exact configured ref. `TRIAL_REF` is read per request; unset or blank turns the trial off, so the proxy remembers nothing, sign-up grants nothing and the line never shows. **The offer also ends at `TRIAL_REF_ENDS_AT`** (ISO 8601, e.g. `YYYY-MM-DDT00:00:00Z`; unset, empty or unparseable = open-ended): from that instant `isTrialOfferOpen()` is false, so the proxy stops setting the cookie, `trialCompUntil` grants nothing even for a cookie set earlier, and the line disappears from `/` and `/signup`. Trials already granted run their full 7 days. Both values are read per request, but on Railway changing a variable redeploys the service. **A referral trial is recognized without a column:** `isLaunchTrialComp` is true when `complimentaryAccessUntil − createdAt` is within ±10 minutes of `TRIAL_DAYS` days; a hand grant does not match (an admin extend on a trial turns it into a manual comp). The admin dashboard shows such accounts with a "Trial · ends {date}" / "Trial ended" badge instead of the Comp badge and counts them on a separate **Referral trials** card (all, plus running) — never in Subscribers unless the account also pays. `/settings/billing` shows a referral-trial user a "Free trial" callout ("Your 7-day Lite trial runs through {date} · {n} days left. No card on file — nothing will be charged. X/Twitter feeds are part of Pro.") and "Pick a plan to keep going after your trial" ("Your free trial is ending" at ≤ 2 days left); a manual comp keeps the "courtesy of the team" copy and reads "Keep your access going" until its last two days, then "Your complimentary access is ending" (the threshold was 7 days, so a week-long hand grant read as ending from day one). **Email verification (RAD-297):** credential signups receive a single-use 24h link (`EmailVerificationToken`, hash-only storage; `app/api/auth/verify-email` → `/verify-email` status page; resend via `POST /api/auth/resend-verification`, rate-limited 3/15min). Unverified accounts keep the full demo (browse, manage feeds) but are blocked at every paid/AI route with 403 `EMAIL_NOT_VERIFIED` — and the background spend paths (Parallel webhook, routing, synthesis sweep) skip unverified owners via `resolveAccessForUserId`. OAuth (Google/Apple) accounts are created already verified (`lib/oauth-user.ts`); existing accounts are grandfathered verified by the migration. Unverified users see a dashboard banner with a resend button (`VerifyEmailNotice`). With no `RESEND_API_KEY` while enforcement is on (production), signup fails **closed** — the account is created unverified and activates once mail returns; the self-host opt-out is explicit (`ALLOW_UNVERIFIED_SIGNUP=1`). **Password reset (RAD-324):** links are DB-backed single-use tokens (`PasswordResetToken`, hash-only, 1h); consuming one sets the password and invalidates every other outstanding link for that account. **OAuth linking (RAD-325):** a provider sign-in is refused (`AccessDenied`) when the address belongs to a credential account that was never verified — the pre-hijacking vector; verified accounts and OAuth-only accounts link normally. Already-subscribed users hitting `POST /api/stripe/checkout` are redirected to `/settings/billing` instead of creating a duplicate session. **Email gate:** checkout requires `User.email` (email is optional in the schema — username/credential signups have none); users set or change it in **Settings → Account** (`PATCH /api/user/email`), which validates format + uniqueness and syncs the Stripe customer email. OAuth (Google/Apple) accounts are read-only there (sign-in matches by provider email). **Webhook idempotency:** `StripeEvent.id` (Stripe's event id) as PK; insert acts as the idempotency fence (P2002 → 200 no-op); handler dispatch runs OUTSIDE any DB transaction so `stripe.subscriptions.retrieve()` doesn't hold a Postgres connection during HTTP round-trip; on handler failure the event row is deleted and Stripe retries (up to 3 days in live mode). `StripeEvent` row carries only `id` + `type` + `processedAt` — no payload column, no retention cron, no PII surface. **Re-fetch from Stripe:** all webhook handlers delegate to `syncSubscriptionFromStripe(id)` which calls `stripe.subscriptions.retrieve()` and upserts — handlers never trust the event payload, eliminating out-of-order delivery bugs by design. **Customer Portal:** `POST /api/stripe/portal` opens self-service flow (cancel at period end, switch monthly↔yearly with proration, update payment method, view invoices). **Subscription gate:** `lib/subscription.ts` exposes `hasActiveAccess` (pure function) and `requireActiveSubscription` (async wrapper returning 402); `lib/paywall.ts` exposes `requirePaidDashboardAccess()` for server-side page-level redirects. **The onboarding demo grant is time-bounded (RAD-294):** `onboardingCompleted === false` grants full access — Pro tier included — only while the account is younger than `ONBOARDING_DEMO_WINDOW_MS` (24h from `User.createdAt`, exported from `lib/subscription.ts`). The bound is enforced **independently** in `hasActiveAccess` and in `subscriptionIncludesTwitter`, because the latter short-circuits on the same condition before it ever delegates — patching one alone leaves the Pro/Twitter path open. `accountCreatedAt` is a **required** input on both functions so `tsc` enumerates every call site; a `select` that omits `User.createdAt` fails to compile rather than silently denying. Paired with this, `onboardingCompleted` is a one-way latch in both writable handlers of `/api/user-settings` (see API_REFERENCE.md) — without it the grant is resettable at will and the time bound buys nothing. Gated API routes (defense-in-depth against curl bypass): `POST /api/feeds`, `POST /api/parse`, `GET /api/parse-stream` (SSE inline), `GET /api/posts/refilter` (SSE inline), `POST /api/posts/group-stories`, `GET /api/posts/group-stories` (SSE inline). Read-only routes stay open so canceled users keep access to their data archive. Status copy: "Renews on X" / "Access until X" (cancelAtPeriodEnd) / "Payment failed — retrying. Access until X" (PAST_DUE grace). Yearly nudge card for active monthly subscribers. Success page polls `GET /api/subscription/status` for up to ~20s after Stripe redirect to handle the webhook race, then routes to `/posts`.

**Knowledge Base (Save → Collections → Library):** A per-user saved-material loop, distinct from Like/Dislike (Save = the user's "keep this / future value" signal). **Save** (`MaterialSaveButton`, a self-contained `Bookmark` action) is optimistic (fill + `.animate-icon-pop`), idempotent per `(userId, materialId)`, and toggles off to unsave. **The Save button is currently removed from the material-card + detail action surfaces** (feedback-focal action-bar redesign, 2026-07-07); the component and its `savedItems` plumbing are retained (Library's `SavedMaterialsGrid` still mounts `MaterialCard`), so re-exposing it is a one-line change. A save lands in a **smart-default topic-collection** (`lib/saved/collections.ts`: most-recently-used collection → the system "Unsorted") surfaced by a `SaveToast` (sonner `toast.custom`) carrying **Move** (re-file or create) + **Undo**. **Manual fragment excerpts** (`ExcerptSaver` wrapping the detail-page content): a text selection raises a floating "Save excerpt" pill; the passage is persisted with source-string offsets as a citation, with a session-only in-text green wash. **Library** is the 4th top-nav peer — `/saved` is a landing grid of collections, `/saved/[collectionId]` a detail view whose top is the **living answer** (`LivingAnswer`): when empty, a dormant promise + **Generate answer** + **Track this** (persisted demand sensor, `Collection.trackRequestedAt`); once generated, an **LLM-maintained cited markdown page** (`Collection.synthesis`/`synthesisDelta`/`synthesisUpdatedAt`, rendered via `react-markdown`) with a "What changed" delta + Refresh. The synthesis (`lib/saved/synthesis.ts` → `regenerateSynthesis`, reusing `createModel()` from `lib/ai.ts`) is **Karpathy LLM-wiki style** — the collection IS the wiki page, the Library is the index, no vector DB; provenance-first ("no claim without a source"). Below it: a `SavedExcerptList` and a `SavedMaterialsGrid` (reuses `MaterialCard`, whose archive/delete cluster auto-hides when no callbacks are passed). Routes: `GET/POST /api/collections`, `POST /api/collections/[id]/track`, `POST /api/collections/[id]/synthesis`, `GET/POST /api/saved`, `DELETE/PATCH /api/saved/[materialId]`, `POST /api/saved/excerpt`, `DELETE /api/saved/excerpt/[id]` — writes gated by `requireActiveSubscription`. **Design rule:** saves feed the KB / topic-collections, **not** the global relevance filter directly (per-user save-signal is ambiguous — "more like this" vs "useful to me"). The card's saved state rides along the material object via a `savedItems` relation added to `fetch-materials-page.ts`. Validation in `lib/validations/saved.ts`; queries in `lib/saved/queries.ts`. Designed as a feature of Radaric rather than a standalone bot. **Self-filling collections ("Track a question"):** a `Collection` can carry a `query` + `cadence` (`POST /api/collections/track`) and is backed 1:1 by a **hidden `EVENT_TRIGGER` `Feed`** (`Collection.monitorFeedId`, `@unique` FK, `ON DELETE SET NULL`) whose Parallel monitor autonomously collects sources; `regenerateSynthesis` reads that feed's APPROVED materials as cited sources alongside any manual saves. Lifecycle in `lib/saved/subscription.ts` — `createTrackedQuestion` (paid-monitor create inside a `$transaction` with a per-user `pg_advisory_xact_lock` cap re-check + monitor rollback on any DB failure), `deleteTrackedCollection` (monitor→feed→collection; keeps the feed flagged on a failed monitor delete so the id survives), `sweepDueCollections` (the worker's **trailing-edge debounce** keyed on `Collection.autoSynthAt`, which `lib/parsers/interest.ts processParallelEvent` bumps on new APPROVED material), `reconcileOrphanMonitors`. **Access gating (RAD-323):** every background spend path — the Parallel webhook (`processParallelEvent`), the routing pass and the synthesis regen — resolves the owner's access from the DB (`lib/subscription.ts hasAccessForUserId`, fail-closed) before spending, so a lapsed account (cancelled subscriber, expired 24h demo) never keeps costing money. `reconcileMonitorsForAccess` (same 2-min worker tick) pauses monitors of lapsed owners, flagging `Feed.accessPaused`, and re-arms only those lapse-paused feeds once access returns — a user-paused feed is never auto-resumed. The worker (`lib/story-aggregator/worker.ts`) runs the sweep every 2 min, independent of GramJS. **The `Feed.hidden` flag is the feed-vs-collection boundary:** a hidden backing feed is excluded from every feed/triage/stats/processing surface (feeds list, sidebar + Inbox count, `fetchMaterialsPage` content + counts, `/api/stats`, `parse`/`parse-stream`, `refilter`, `group-stories`, `analytics/accuracy`, `categories/custom`, `clear`/`bulk-delete`) and its feed `PATCH`/`DELETE` are rejected (`409`) — it's managed through its collection so `Collection.monitorFeedId` can't desync from `Feed.parallelMonitorId`. **Routing (Slice 2):** a tracked question also pulls in matching material from the user's NORMAL feeds. The worker pass `lib/saved/routing.ts routeRecentMaterials` (in the same 2-min self-filling tick) routes each APPROVED non-hidden-feed material into any tracked question whose query it matches via a `CollectionMaterial` join (distinct from `SavedItem` so it can't collide with manual saves). `Material.routedAt` is the per-material watermark (advanced only on a clean run; transient AI failures retry). Matching = a cheap whole-word keyword pre-filter → `evaluateMaterialsBatch({ criteria })`, the clean tracked-question eval (query as the sole criterion + blacklist; suppresses the feed's customPrompt/categories/feedback). Cost bounded by `ROUTING_BATCH_LIMIT` / `ROUTING_USER_RUN_EVAL_CAP` / `ROUTING_USER_DAILY_CAP`. The synthesis + collection grid/counts union saves + backing-feed materials + routed materials (URL-deduped). **Source discovery (Slice 3):** `lib/saved/discovery.ts discoverSourcesForTopic` (via `POST /api/collections/[id]/discover`, subscription-gated + a per-(user,collection) in-memory cooldown) LLM-suggests reputable sources for the question and validates each into a real RSS feed (`validateFeed` = `isAllowedUrl` SSRF guard + AbortSignal-bounded fetch + parse, with a `detectRSSFeed` site-probe fallback); only resolvable feeds are returned (RSS-only by design). The `DiscoverSourcesDialog` on the collection detail adds chosen feeds via the canonical `POST /api/feeds`; Slice-2 routing then pulls their content into the question. **Cadence freshness floor (Slice 4):** besides the armed trailing-edge debounce, `sweepDueCollections` also regenerates a tracked answer when it's older than the question's cadence (HOURLY/DAILY/WEEKLY) AND there's material newer than it — a safety net for a missed `autoSynthAt`-arm and the first synthesis of a never-generated question (floor predicates match the synthesis exactly so it can't loop; only for collections with no pending arm). Capped per tick (`SWEEP_MAX_REGENS`); the floor probe is throttled in the worker (`SELF_FILLING_FLOOR_INTERVAL_MS`, 15 min) with an overlap guard. `POST /api/collections/regenerate-due` (secret-auth `WORKER_TRIGGER_SECRET`, timing-safe) is a **manual/ops** trigger for the same sweep — **not** a cron (the worker runs it every 2 min). **On-demand pull:** autonomous delivery is cadence-push only (Parallel → webhook → `processParallelEvent`), but `POST /api/collections/[id]/refresh` (the **"Check for updates"** button on a tracked question) fetches the monitor's latest events directly (`parseInterestSource`), ingests + evaluates them, and regenerates the answer inline — the verify-now path that doesn't wait for the cadence. Subscription-gated; 30s per-(user,collection) cooldown (released on failure so a transient Parallel error doesn't lock out a retry).
